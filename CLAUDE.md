# footyplanner

A map of European football fixtures for planning trips. One Cloudflare Worker serves the page, the API (`/api/*`, `/img/*`) and a cron that copies ESPN data into D1. The rebuild plan, its step order and the open follow-ups are in `docs/PLAN.md`; read it before starting work. Use the terms in `GLOSSARY.md`.

## Layout

- `apps/api`: the Worker. Hono routes in `src/routes/`, cron ingestion in `src/ingest/` (entry point `run.ts`), Drizzle schema in `src/db/schema.ts`, migrations in `migrations/`.
- `apps/web`: the React app (Vite), served at `/next/` until step 3e moves it to `/`. `src/` for components, the Hono RPC client and TanStack Query hooks; `e2e/` for Playwright tests and their seed data.
- `apps/web/legacy`: the old single-file page, copied into the build and served at `/` until step 3e.
- `packages/shared`: types and helpers used by both the API and the page.
- `packages/eslint-plugin`: the repo's own lint rules.
- `docs/adr/`: architecture decision records.

## Commands

- `pnpm format:check && pnpm lint && pnpm typecheck && pnpm test && pnpm build && pnpm e2e`: the same checks CI runs. Run them all before committing.
- `pnpm build`: builds the React app and copies the legacy page into `apps/web/dist`, which the Worker serves.
- `pnpm dev`: `wrangler dev` with local D1 and R2, serving the last build. `pnpm --filter @footyplanner/web dev` runs Vite with hot reload at `http://localhost:5173/next/`, proxying `/api` to it.
- `pnpm e2e`: Playwright against `wrangler dev` with a separate seeded local database.
- The web app imports the API's types from `apps/api/dist/rpc/`, generated by `build:rpc`; its typecheck runs that first.
- After changing `apps/api/wrangler.jsonc`, run `pnpm --filter @footyplanner/api types`, or typecheck fails on stale `worker-configuration.d.ts`.
- After changing `src/db/schema.ts`, run `pnpm --filter @footyplanner/api db:generate` and commit the new migration.

## Rules

- No comments in code; lint enforces it (`packages/eslint-plugin`). Code reads clearly through naming and small functions, and any design decision that needs explaining gets an ADR in `docs/adr/` (template in `docs/adr/README.md`, added to its index).
- Before any change, call the `start-work` skill.
- A pull request is complete before it's opened: its ADRs, the status line and step entry in `docs/PLAN.md`, and the checks under Commands all green. Then fetch and rebase on `origin/main`, rerunning the checks if anything came in. Push to an open pull request only for review changes.
- Wait for CI with `gh pr checks <number> --watch`; right after `gh pr create` it can report no checks yet, so run it again. After a `[JFDI]` push to `main`, report the push and stop.
- Merging to `main` deploys: CI applies D1 migrations to production, then runs `wrangler deploy`. Migrations must be safe to apply before the new code is live.
- Visitor requests never call ESPN or Photon. Only the cron fetches upstream data.
- Test-driven development for code changes: follow "Tests come first" in `CODING_STANDARDS.md`, which review checks, including recording each red run for the PR description.
- Tests run inside workerd against local D1 and R2 (`@cloudflare/vitest-plugin`), with ESPN and Photon faked as "Tests never call the real APIs" in `CODING_STANDARDS.md` describes.

## Cloudflare Free plan limits

Code has to fit these; going over fails or stops the site rather than billing.

- 10 ms CPU per invocation, including each cron run. Production runs currently exceed this (see Follow-ups in `docs/PLAN.md`).
- 50 subrequests per invocation. Fetches, D1 queries and R2 calls all count; a D1 batch counts as one.
- D1: 100 bound parameters per query, and 100k rows written a day. Going over the write limit stops every query until 00:00 UTC, so never rewrite unchanged rows.
- 100k Worker requests a day.

## Checking production

- `https://footyplanner.footyplanner-api.workers.dev/api/status`: last cron run, months fetched, pending venues and crests.
- `npx wrangler tail footyplanner` (from `apps/api`): live logs with CPU time per run. Live only; it can't show past runs.
- Past CPU time (e.g. overnight): the GraphQL Analytics API at `https://api.cloudflare.com/client/v4/graphql`, dataset `workersInvocationsAdaptive` filtered on `scriptName: "footyplanner"`, grouped by `datetimeHour`, with `quantiles { cpuTimeP50 cpuTimeP99 }` (microseconds). wrangler's OAuth token works (`oauth_token` in `~/Library/Preferences/.wrangler/config/default.toml`). It mixes HTTP requests with ingest runs; ~60 invocations an hour with few subrequests means ingest runs only. `workersInvocationsScheduled` returns nothing, and the Workers Observability query API returns Forbidden for wrangler's token.
- `npx wrangler d1 execute footyplanner --remote --command "…"`: query the production database (`ingest_runs`, `ingest_queue`, `fixture_changes`).
